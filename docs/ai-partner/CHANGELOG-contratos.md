## 2026-10-12 — S2b + S4b do `sourceLabel` (decisão C — MUDANÇA DE CONTRATO e de SEMÂNTICA do E5b)
- **`ImportRef.reproducibility.exitReasonMap`** deixa de carregar o regex do usuário: cada regra vira `{ patternRef: "pat_<24 hex>", reason }`, na MESMA ordem (a primeira que casa vence). `patternRef = SHA-256("meutrade/patternRef/1" ‖ sal ‖ texto exato do padrão)` (sensível à caixa; mesmo sal opcional; pseudônimo — ver §14.14). O regex fica **só** no `ImportRecord` interno. Schema: `ReproducibilityEvidenceSchema`; a chave `pattern` ou um `patternRef` malformado ⇒ `INVALID_FORMAT` (inclusive com selo refeito). **Mapa vazio (todas as fixtures reais e sintéticas): nada muda — o `evidenceHash` dos 9 bundles pinados continua provado.**
- **E5b — semântica nova (dita, não escondida):** para um import com mapa **não vazio**, o `ImportRef` não traz o regex, então o E5b **não reinge sozinho**: o chamador informa `exitReasonMap` (a opção já existia) e o E5b o confere **regra a regra, na ordem**, contra os `patternRef` e os motivos registrados. **Mapa ausente ⇒ `UNVERIFIABLE` (`S_CONTEXT_INSUFFICIENT`); mapa divergente (ordem, regra a mais/menos, motivo, caixa) ⇒ `UNVERIFIABLE` (`S_CONTEXT_INSUFFICIENT`); import salgado sem o sal ⇒ `UNVERIFIABLE` (`S_ACCOUNT_REF_UNVERIFIED`) — nunca adulteração, nunca `FAIL`.** Mapa informado a um import SEM mapa é ignorado (o registro manda, como antes). Imports anteriores ao registro (sem `reproducibility`) seguem usando o mapa do chamador como sempre.
- **Requisito de contrato (já valia para `strategyRef`/rótulos; agora vale também para o `patternRef`):** quem gera a Evidence precisa passar o **mesmo sal do import** (`accountRefSalt` em `explainMetric`/`explainDerived`/`explainTrades`) — sem isso `strategyRef`, `labelRef` e `patternRef` saem calculados com sal vazio e a verificação com o sal certo não os reproduz (⇒ `UNVERIFIABLE`).
- Testes existentes ajustados (`test-evidence-import-context.mts`): o `ImportRef` = `projectReproducibility(record)` (patternRef); o E5b com mapa recebe o mapa; o mapa com nome de conta **não chega à Evidence** (garantia estrutural; antes só a trava fail-closed o barrava). Novo: `test-evidence-sourcelabel-s4b.mts` (8; tabela dos 4 casos rodada contra código real).

## 12/10/2026 — Política de sal P4: o E5b LÊ `saltId`/`saltCheck` (mudança de comportamento só para bundles COM a declaração)
`VerifySourceOptions.salt = { provider, userId }`. `saltId` resolvível ⇒ usa esse sal e compara os refs de verdade; `saltCheck` é autodeclaração redundante, **nunca portão**: refs batem + check diverge ⇒ `SOURCE_VERIFIED_PARTIAL` + `L_SALT_CHECK_DIVERGENT`; refs divergem ⇒ `SOURCE_MISMATCH` (+ `V_SALT_CHECK_MISMATCH` se o check também diverge; nunca `UNVERIFIABLE`). `saltId` não resolve ⇒ tenta os sais conhecidos do usuário (`L_SALT_ID_NOT_RESOLVED`, PARTIAL) e só então `UNVERIFIABLE` (`S_SALT_UNKNOWN`/`S_SALT_RETIRED`; resíduo documentado: indistinguível de sal aposentado). Provider vence a string `accountRefSalt`. `saltId`/`saltCheck` deixam de contar como divergência do registro. Novo (V14): `saltId` em import sem sal ⇒ `V_SALT_DECLARATION_INCONSISTENT`. **Também:** `combine()` agora deixa o SKIPPED bloqueante vencer o parcial (já era a intenção documentada). Bundles sem `saltId`: inalterados (baseline linha a linha idêntico; 699 → 711 ✓ = +13 do P4, −1 do teste transitório do P2).
